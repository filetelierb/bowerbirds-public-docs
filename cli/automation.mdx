## Prefer JSON and retain receipts

```sh
bucket_json=$(bowerbirds bucket create "Build evidence" --json)
bucket_slug=$(printf '%s' "$bucket_json" | jq -r '.slug')

item_json=$(bowerbirds import "$bucket_slug" ./test-results/screenshot.png \
  --title "Failed visual assertion" \
  --json)
item_id=$(printf '%s' "$item_json" | jq -r '.id')
```

Inspect one real receipt before relying on its fields. Commands run with `--follow --json` may produce newline-delimited event objects rather than one JSON document.

## Use local paths for binary handoff

Avoid base64 in shell arguments. `bowerbirds import` copies a readable path into the managed store; `item fetch`, `capture export`, and `bucket fetch` write selected data back to disk.

## Make retries safe

- Check whether a Bucket or record already exists before creating it again.
- Treat output paths as write-once. Item and Bucket fetches refuse existing destinations, while capture export can overwrite files inside its destination; use a fresh directory for capture bundles.
- Read a Scratchpad immediately before passing `--revision`.
- Treat a failed Package validation as an incomplete result even if the draft was saved.
- Keep the returned item ID and payload name together.

## Run as an agent, not as a person

Automation that acts on cloud records should hold its own credential. On a machine with a browser, `bowerbirds cloud tokens login` obtains one through OAuth; on a CI runner, present a token minted by hand through `BOWERBIRDS_TOKEN`. Sign the records the job handled (`cloud records sign`) so the next run's `--unsigned` listing starts where this one stopped.

## Check the executable first

```sh
bowerbirds server info --json
```

Use the receipt to confirm the active Bowerbirds version and available capabilities before running an automation.
